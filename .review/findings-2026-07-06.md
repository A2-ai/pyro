## 1. Architecture summary

pyro is a small R package (~1,060 lines R, ~230 lines bash/PowerShell) wrapping
the `uv` CLI to give R projects reproducible project-local Python environments.
Consumers are the sibling fyr packages (reportifyr, presentifyr) plus direct
users. It is layered in three tiers, and the layering is real and clean:
(1) a declaration layer, `write_group_to_pyproject()`, which only edits the
project `pyproject.toml`; (2) a materialization layer, `initialize_python()`,
which seeds/audits the toml then delegates all uv install/lock/sync work to a
bundled platform script; (3) a runtime layer, `get_venv_uv_paths()` +
`run_python_script()`. Two cross-cutting spines run under all three: the
hand-rolled TOML parser/splicer in `R/write_group_to_pyproject.R` (every toml
read or write in the package goes through it, confirmed: consumers at
`R/audit_pins.R:36,47` and `R/initialize_python.R:182,225`), and the
session-global `options("venv_dir")` project-root cache.

**Addendum spot-checks.** The repo map holds up. All seven NAMESPACE exports
match the listed entry points; the claimed highest fan-in module
(`write_group_to_pyproject.R`) is confirmed; the two `(?)` items are resolved:
`inst/extdata/uv.lock` is indeed referenced by no code, test, or script (grep
over R/, tests/, inst/, workflows), and `r-release.yml` (477 lines) plus
`deploy-prism.yml` (269 lines) are templated A2-ai release/publish workflows
with nothing alarming beyond one vignette question (section 4).

**Flows traced.** (a) Happy-path init: `initialize_python()` -> prompt -> seed ->
`audit_pins()` -> uv discovery/version adoption -> `processx::run` of
`uv_setup.sh|ps1` -> `uv lock` + `uv sync --frozen`. (b) Merge path:
`write_group_to_pyproject()` -> `read_dep_groups()` -> case dispatch -> splice +
`writeLines`. (c) Runtime error path: `run_python_script()` -> `processx::run`
with `VIRTUAL_ENV` -> tryCatch discards the condition and rethrows a constant
string.

**Refutations (from H1 sub-hypotheses).** (i) The `^\s*\[` block-end regex at
`R/write_group_to_pyproject.R:166` is safe against array continuation lines in
*valid* dep-groups tables: items are quoted strings or inline tables, so a
continuation line cannot begin with `[` without the file already being invalid
TOML. (ii) Duplicate `[dependency-groups]` headers: pyro edits only the first
table (verified empirically) but a duplicate table is already invalid TOML that
uv rejects, so pyro cannot make a valid file worse here. (iii)
`[dependency-groups.name]` sub-tables are not valid PEP 735 and are outside
plausible input space.

**Overall read.** The macro-architecture is genuinely good for the package's
size: crisp layer boundaries, one toml module, one uv-work module, explicit
contracts in roxygen and vignettes. The systemic risk is concentrated in three
places where a stated guarantee is not backed by mechanism: the hand-rolled
TOML splicer can silently corrupt the very file the package promises never to
damage; the uv discovery/install policy exists in three divergent copies; and
the session-global root cache silently retargets defaults after a project
switch. The Windows path is entirely unexercised by tests and has a concrete
argument-binding bug.

## 2. Primary findings (ranked)

### F1. TOML splicer silently corrupts user `pyproject.toml` on non-string-array content

- **Severity:** Critical. **Category:** A/D (duplicated domain concept, trust
  boundary). **Confidence:** High (reproduced by executing the package code).
- **Evidence:** `R/write_group_to_pyproject.R:193-238` (`parse_group_entries`),
  `:284-291` (`extract_quoted`), `:250-276` (`close_bracket_pos`), `:369-423`
  (`replace_subgroup`), rewrite entry at `:100-113`.
- **The issue:** The parser models a dependency group as an array of quoted
  strings only. Two legal-TOML inputs corrupt the file on the case-4a rewrite
  path (which fires whenever the spec contains a dep name the user's group
  lacks, i.e. any time pyro or a wrapper adds a dep):
  1. **PEP 735 include-group items.** `{include-group = "base"}` is parsed by
     `extract_quoted` as the plain string `"base"`; the rewrite emits it as a
     string literal. Reproduced: `reportifyr = [{include-group = "base"}, "pillow==11.1.0"]`
     becomes `reportifyr = ["base", "pillow==11.1.0", "pyyaml==6.0.2"]`. The
     include-group reference is silently converted into a PyPI dependency named
     `base`. uv will then try to resolve a real package called `base`, and the
     user's group composition is destroyed with no error and no message.
  2. **Comments containing `]` inside multi-line arrays.**
     `close_bracket_pos()` has no comment handling, so
     `# keep pillow pinned [see docs]` terminates the array early. Reproduced:
     the rewrite splices the new subgroup over the comment line and leaves the
     real entries orphaned below it:
     ```
     reportifyr = [
         "pillow==11.1.0",
         "pyyaml==6.0.2",
     ]
         "pillow==11.1.0",
     ]
     ```
     This is invalid TOML; the next `uv lock` fails and the file needs manual
     repair. The read-only consumers (`audit_pins`, `seed_pyproject`) also see
     an empty entry set for such a group, so the audit silently reports nothing.
- **Blast radius:** Breaks the package's central guarantee
  (`vignettes/how-it-works.Rmd:18-19`: "pyro never owns or rewrites the user's
  pins"). It fires under realistic conditions: any user who adopts PEP 735
  include-groups (uv supports and promotes them) or writes a bracketed
  comment, combined with any bundled-spec dep addition or a wrapper passing an
  extended `deps`. Corruption is silent in mode 1 and delayed to the next lock
  in mode 2.
- **Remediation sketch:** Either (a) make `parse_group_entries` recognize the
  constructs it cannot model, and make case 4a refuse to rewrite (warn +
  return `FALSE`) when the subgroup body contains anything other than string
  literals (comment lines, inline tables), or (b) use a real TOML reader for
  the read side and keep the splicer only for arrays verified to be plain.
  Option (a) preserves the zero-dependency stance and is ~1 day including
  tests; the detection is cheap (scan the subgroup body for `{` or `#` outside
  quotes before rewriting).

### F2. No PEP 503 name normalization: pyro adds conflicting duplicate pins and the audit goes blind

- **Severity:** High. **Category:** A/D. **Confidence:** High (reproduced).
- **Evidence:** `R/write_group_to_pyproject.R:320-322` (`pkg_name_of`),
  `:301-311` (`merge_deps`); consumers `R/audit_pins.R:51-63` and the case
  dispatch at `R/write_group_to_pyproject.R:100-117`.
- **The issue:** Python package names are case-insensitive with `-`/`_`/`.`
  equivalence (PEP 503). `pkg_name_of()` does no normalization, and it is the
  only name-identity mechanism in the package. Reproduced: a user group
  containing `"Pillow==10.0.0"` merged against spec `"pillow==11.1.0"` produces
  `reportifyr = ["Pillow==10.0.0", "pillow==11.1.0"]`, two contradictory pins
  for the same package, so the next `uv lock` fails to resolve. The same miss
  makes `audit_pins()` silent on `Pillow==10.0.0` vs bundled `pillow==11.1.0`
  and `python_docx` vs `python-docx` (reproduced: zero messages emitted).
- **Blast radius:** In merge, this effectively *overrides* the user's pin
  intent and breaks their project at lock time, violating "user pins win"
  through the back door. In audit, exactly the drift the feature exists to
  surface is hidden. Both consumers of the one helper are wrong the same way,
  so fixing the helper fixes both.
- **Remediation sketch:** Normalize in one place:
  `norm_name <- function(x) tolower(gsub("[-_.]+", "-", pkg_name_of(x)))` and
  compare normalized names in `merge_deps` and `audit_pins`. Hours, plus tests
  for the case/underscore variants.

### F3. Stale session-global `options("venv_dir")` cache silently retargets every default-path operation

- **Severity:** High. **Category:** A/E (implicit temporal coupling, config).
  **Confidence:** High.
- **Evidence:** Write sites `R/initialize_python.R:78-81` (set only if unset)
  and `R/venv.R:17-21` (set only if unset); the read site is the default for
  everything: `R/get_proj_dir.R:23`, which backs the defaults of
  `initialize_python()` (`:50`), `write_group_to_pyproject()` (`:50`), and
  `audit_pins()` (`:32`).
- **The issue:** The first init (or first `get_venv_uv_paths()`) in a session
  pins the option; nothing ever updates or invalidates it. Concretely: init
  project A (option = A), then `initialize_python(venv_dir = B)`. The B init
  itself is correct because it uses the explicit arg, but the option still says
  A, so every subsequent defaulted call, `write_group_to_pyproject("x")` from a
  wrapper, `audit_pins()`, `get_venv_uv_paths()` before a
  `run_python_script()`, reads and *mutates project A*, the project the user
  has mentally left. A wrapper calling `write_group_to_pyproject()` then
  `initialize_python(groups=...)` with defaults will splice its group into A's
  toml and sync A's venv while the user believes they are working in B. There
  is no message on the stale-read path (only on first set, `R/venv.R:19`), and
  no API to clear the cache other than knowing the option name.
- **Blast radius:** Wrong-project toml mutation and wrong-venv execution in any
  multi-project session (project switches, monorepos, package developers
  testing in temp dirs). Because the option is un-prefixed and global, the two
  host packages also share the slot: the first package to run decides the root
  for all of them for the rest of the session. (The option's *name* is
  compat-frozen and not flagged, per the addendum; the staleness is the issue.)
- **Remediation sketch:** Update the cache whenever an explicit
  `venv_dir`/`pyproject_dir` is supplied (`options(venv_dir = venv_dir)`
  unconditionally in `initialize_python()`), emit a message when a cached value
  is used that differs from `here::here()`, and export a small
  `set_proj_dir()`/`clear_proj_dir()` pair. Hours; the risky part is deciding
  the precedence story once and documenting it in `get_proj_dir()`.

### F4. Windows multi-group init cannot bind `-Groups` through `powershell.exe -File`, and no test would catch it

- **Severity:** High. **Category:** B/D (platform contract drift).
  **Confidence:** Medium-high (mechanism verified against documented PowerShell
  semantics; no Windows host available to execute).
- **Evidence:** `R/initialize_python.R:124-134` builds
  `c("-ExecutionPolicy","Bypass","-File", cmd, venv_dir, pyproject_dir, uv_version, "-Groups", g1, g2, ...)`;
  `inst/extdata/uv_setup.ps1:19-34` declares `[string[]]$Groups`; the ps1's own
  header comment (`uv_setup.ps1:1`) documents the comma form
  `-Groups <a>,<b>,...`, which is not what R sends.
- **The issue:** `powershell.exe -File` does not support passing arrays to
  parameters (documented limitation). With `-Groups a b`, `a` binds to
  `$Groups` and `b` then fails positional binding (positions 0-2 are consumed
  by the three path/version parameters), so PowerShell exits with a parameter
  binding error before the script body runs and `processx::run` throws. Even
  the comma form would arrive as the single literal string `"a,b"` under
  `-File`, producing `uv sync --group "a,b"` and a uv error. Net effect:
  `initialize_python(groups = c("reportifyr", "presentifyr"))`, the documented
  multi-wrapper pattern, cannot work on Windows. Single-group calls bind and
  work.
- **Blast radius:** Every Windows user of the multi-group flow; the failure is
  an opaque PowerShell binding error surfaced through processx. It is invisible
  to CI because every `initialize_python` test carries `skip_on_os("windows")`
  (`tests/testthat/test-initialize_python_groups.R:36,56,79,103,128,155,172`),
  so the Windows matrix cell in `.github/workflows/R-CMD-check.yaml:24`
  exercises nothing platform-specific (see F8).
- **Remediation sketch:** Pass groups as one delimited string
  (`"-Groups", paste(groups, collapse = ",")`) and split inside the ps1
  (`[string]$Groups` then `-split ','`), or invoke via `-Command` with proper
  quoting. Hours, plus a ps1 CI test with a stubbed uv (see F8).

### F5. uv discovery/version/install policy exists in three divergent copies; runtime can use a different uv than the one init installed

- **Severity:** High. **Category:** A/E (duplicated concept with drift).
  **Confidence:** High for the divergence, medium for how often it bites.
- **Evidence:** `R/uv_path.R:21-47` (PATH first, then `~/.local/bin`, then
  `~/.cargo/bin`); `inst/extdata/uv_setup.sh:66-81` (prepends `~/.local/bin`
  to PATH, then `command -v uv`; never looks at `~/.cargo/bin`; installs from
  GitHub releases, `:54-56`); `inst/extdata/uv_setup.ps1:49-92` (prepends
  `%USERPROFILE%\.local\bin`; installs from `astral.sh`, `:58`); version
  adoption in `R/initialize_python.R:94-105`.
- **The issue:** Three different answers to "which uv is *the* uv":
  R prefers the PATH binary; both scripts prefer `~/.local/bin`; only R knows
  about `~/.cargo/bin`. Enumerated states that misbehave:
  - **Pinned version, different PATH uv.** `options(uv.version = "0.7.8")`,
    system uv 0.9.x on PATH (e.g. Homebrew). Init installs 0.7.8 into
    `~/.local/bin` and locks/syncs with it. Later,
    `get_venv_uv_paths()` -> `get_uv_path()` returns the *PATH* uv (0.9.x), so
    `run_python_script()` executes the venv with a uv version that never
    locked it. The version pin is enforced at install time only, not at
    runtime binary selection, and nothing reports the split.
  - **User-managed `~/.local/bin/uv` at another version.** The script's
    mismatch branch (`uv_setup.sh:75-77`, `uv_setup.ps1:86-88`) reinstalls the
    required version *over* the user's binary. A user who manages uv
    themselves has it silently replaced by every pyro init with a different
    pin.
  - **uv only in `~/.cargo/bin`.** R finds it and adopts its version
    (`R/initialize_python.R:96`), then the script cannot see that binary and
    installs a duplicate into `~/.local/bin`; which one runs later depends on
    PATH.
  - **Source asymmetry.** sh fetches from
    `github.com/astral-sh/uv/releases/...`, ps1 from `astral.sh`. On networks
    that allowlist one origin, install succeeds on one platform and fails on
    the other; ps1 also validates the version format (`uv_setup.ps1:29`) while
    sh accepts anything.
- **Blast radius:** Version drift between lock time and run time, silent
  clobbering of user-managed uv installs, and platform-split install failures.
  Every future change to discovery or install policy must be made in three
  files with no mechanism keeping them in sync; this already happened once
  (`NEWS.md` 0.1.1 fixed a message that had drifted between the copies).
- **Remediation sketch:** Make R the single decider: `get_uv_path()` resolves
  the binary, R passes the *resolved absolute path* to the scripts, and the
  scripts only install (into a pyro-chosen prefix) when R passes none, then
  echo back the installed path. Removes both discovery copies and the
  clobbering branch. ~1-2 days including both scripts and tests.

### F6. Runtime venv targeting rests on cwd, not on the `venv_path` argument; `uv run` also bypasses the `--frozen` policy

- **Severity:** Medium. **Category:** A/D. **Confidence:** Medium (uv behavior
  is documented but version-dependent; not executed here).
- **Evidence:** `R/run_python_script.R:42-62` sets only `VIRTUAL_ENV` and
  passes caller args (canonically `c("run", "-m", ...)`, `:11,29`) with no
  `--project`, `--directory`, or `UV_PROJECT_ENVIRONMENT`; contrast the init
  layer, which pins the target explicitly via `UV_PROJECT_ENVIRONMENT` and
  `--project` (`inst/extdata/uv_setup.sh:87-92`, `uv_setup.ps1:94-99`).
- **The issue:** For project commands like `uv run`, uv discovers the project
  by walking up from the *current working directory* and, when `VIRTUAL_ENV`
  does not match that project's environment, warns and ignores it (uv's
  documented behavior since 0.4.x, unless `--active` is passed). So the
  carefully resolved `venv_path` from `get_venv_uv_paths()` is largely
  decorative: which venv actually executes is decided by the R session's cwd.
  When cwd is the project root (the common here::here case) this coincides and
  everything works, which is why it has not been noticed. When cwd is
  elsewhere, e.g. a knitr working directory, an LLM-agent layout where
  `pyproject_dir != venv_dir != cwd`, or a different project entirely, `uv run`
  targets (and, by default, locks and *syncs*) whatever project it discovers
  from cwd. The runtime layer thereby performs implicit non-`--frozen` syncs,
  while the materialization layer promises frozen-only materialization.
- **Blast radius:** Wrong-venv execution and surprise lockfile/venv mutation in
  non-default layouts, precisely the layouts `pyproject_dir` was added to
  support (`R/initialize_python.R:33-37`). Compounds with F3 (a stale root
  cache hands out the wrong `venv_path`, and nothing downstream would even use
  it).
- **Remediation sketch:** In `run_python_script()`, pass the target explicitly:
  set `UV_PROJECT_ENVIRONMENT = venv_path` (and/or inject
  `--project <dir>` / `--no-sync` ahead of caller args when `args[1] == "run"`).
  Hours, plus a decision on whether runtime syncing is ever wanted.

### F7. Subprocess errors: the condition object is destroyed at one boundary and unfiltered at the others

- **Severity:** Medium. **Category:** B. **Confidence:** High.
- **Evidence:** `R/run_python_script.R:55-66` (tryCatch discards `e`, rethrows
  the constant `paste0(script_name, " failed.")`); `R/initialize_python.R:134,143`
  (raw processx error propagates untouched) and `:153` (script stdout printed
  only on success, so on failure the installer's progress output is lost);
  `R/uv_path.R:75-79` (`get_uv_version` propagates raw processx errors, e.g.
  ENOENT on a stale path).
- **The issue:** The de facto strategy is one-third destroy, two-thirds leak.
  At the boundary host packages are told to program against ("wrap this call
  in tryCatch() if you want to act on a subprocess crash",
  `R/run_python_script.R:8`), the caught condition carries exit status, the
  stderr tail, and the ENOENT-vs-nonzero-exit distinction, and all of it is
  discarded; the caller receives a constant string with no condition class, no
  parent, and no fields. A host package cannot distinguish "uv binary missing"
  from "Python raised an exception" from "killed by signal" without
  re-implementing the subprocess call. Meanwhile init errors surface raw
  processx internals to end users. (stderr *routing* is intentionally the
  caller's concern and is not flagged; the discarded condition object is.)
- **Blast radius:** reportifyr/presentifyr error handling and user-facing
  diagnostics for every Python failure; support burden ("my report failed:
  'run_reportifyr.py failed.'"). It also forecloses retry/fallback logic in
  hosts.
- **Remediation sketch:** Rethrow a classed condition preserving the parent:
  `rlang::abort(paste0(script_name, " failed"), class = "pyro_subprocess_error", parent = e, status = e$status)`,
  and wrap the other two call sites with the same class so there is one error
  contract. Hours.

### F8. Test coverage is anti-correlated with risk: the installer scripts and the Windows branch have zero coverage

- **Severity:** Medium. **Category:** E. **Confidence:** High.
- **Evidence:** No test executes or lints `inst/extdata/uv_setup.sh` or
  `uv_setup.ps1` (grep over `tests/`); every `initialize_python` test skips
  Windows (`tests/testthat/test-initialize_python_groups.R:36,56,79,103,128,155,172`);
  all subprocess boundaries are stubbed (`mockery::stub(..., "processx::run", ...)`),
  so the R-to-script argument contract is asserted only against itself; the
  parser tests (`tests/testthat/test-write_group_to_pyproject.R`) cover exactly
  the string-array forms the parser handles and none of the forms that corrupt
  (include-group, comments, F1).
- **The issue:** The three most load-bearing artifacts, the two scripts and the
  toml splicer's edge cases, have the least coverage, while the simple pure
  paths (audit messaging, path lookup) are tested exhaustively. The Windows CI
  cell (`.github/workflows/R-CMD-check.yaml:24`) therefore green-lights a
  platform branch that contains a real bug (F4). The 0.1.1 NEWS entry shows
  script behavior already drifted once without a test noticing.
- **Blast radius:** Every regression class this review found (F1, F4, F5)
  lives precisely in the untested zone; future edits there ship blind.
- **Remediation sketch:** Three cheap layers: (1) a bats or plain-bash test
  that runs `uv_setup.sh` against a stub `uv` on PATH and asserts the
  lock/sync argv; (2) the same for ps1 via `pwsh` (available on all GitHub
  runners including Linux), which would have caught F4 immediately; (3) drop
  `skip_on_os("windows")` from the mocked `initialize_python` tests, which do
  not actually need Unix. ~1-2 days.

### F9. `pyproject.toml` writes are non-atomic read-modify-write with no locking

- **Severity:** Medium. **Category:** C/D. **Confidence:** Medium (mechanism
  certain, frequency depends on usage).
- **Evidence:** `R/write_group_to_pyproject.R:78` (read) then `:85,94,107`
  (direct `writeLines` to the same path); `R/initialize_python.R:235` (seed
  write); no locking or temp-file rename anywhere in the package.
- **The issue:** Two R sessions (parallel CI jobs, a console plus a background
  render) that both run wrapper init flows perform concurrent
  read-modify-write on one `pyproject.toml`. Interleavings lose one wrapper's
  group entirely (last write wins on the full file) or let a reader observe a
  partially written file, and a crash mid-`writeLines` truncates the toml. uv
  locks its own operations but cannot protect pyro's R-side splice.
- **Blast radius:** Occasional, hard-to-reproduce "my group disappeared" or
  corrupt-toml reports, most likely in CI matrices that init in parallel jobs
  sharing a workspace.
- **Remediation sketch:** Write to `pyproject.toml.tmp` + `file.rename()` for
  atomicity (hours); if concurrent sessions are in scope, add an advisory lock
  file around the read-modify-write (~a day).

### F10. Bare Enter at the `[Y/n]` prompt errors instead of accepting the advertised default

- **Severity:** Low. **Category:** F. **Confidence:** High.
- **Evidence:** `R/initialize_python.R:283-287` (prompt advertises `[Y/n]`),
  `:61-71` (`readline` returns `""` on Enter; `tolower("") != "y"` and
  `"" != "n"` routes to `stop("Must enter Y or n.")`).
- **The issue:** The `[Y/n]` convention promises that Enter means yes; pyro
  hard-errors instead. (The exact-lowercase-`"n"`-only decline is intentional
  fail-closed behavior per the survey and is not flagged.)
- **Blast radius:** First-run friction for every interactive user who follows
  the convention.
- **Remediation sketch:** Treat `""` as `"Y"` in the dispatch at `:61`. Minutes.

## 3. Low-hanging fruit

- `inst/extdata/uv.lock` (222 lines): referenced by no code, test, script, or
  doc; dead weight shipped in every install. It currently matches the bundled
  toml's pins, but nothing keeps it fresh when a pin bumps, and its presence
  implies seeding copies a lockfile (it does not). Fix: delete it, or add a
  test asserting sync with the bundled toml.
- `inst/extdata/uv_setup.ps1:61-63`: the `$LASTEXITCODE` check after
  `Invoke-Expression` is unreliable. Invoke-Expression of a PS script does not
  set `$LASTEXITCODE`; on the fresh-install path no native command has run
  yet, and under `Set-StrictMode -Version Latest` referencing the unset
  automatic variable itself throws. The check is dead-or-crashing code either
  way. Fix: rely on `$ErrorActionPreference='Stop'` plus a post-install
  `Get-Command uv` re-probe (mirroring `uv_setup.sh:59-62`).
- `R/write_group_to_pyproject.R:327-333` (`render_subgroup`): deps are pasted
  into `"` quotes unescaped; a caller-supplied dep containing a double quote
  produces invalid TOML. Fix: reject `"` and newlines in `deps` at the
  `write_group_to_pyproject()` boundary alongside the existing name check.
- `R/write_group_to_pyproject.R:369-423`: a case-4a rewrite silently deletes
  user comment lines *inside* the rewritten subgroup even in the benign
  plain-string case (verified: `# our pinned imaging lib` vanishes). Subsumed
  by F1's remediation; listed because it happens on fully valid input too.
- `R/uv_path.R:78`: `strsplit(result$stdout, " ")[[1]][2]` yields `NA` (not an
  error) if uv's version banner format changes; downstream `uv_version`
  becomes the literal string "NA" handed to the installer. Fix: regex-extract
  a semver token and stop on no-match.
- `R/initialize_python.R:153`: `message(result$stdout)` dumps the entire
  installer transcript as one message on success, while on failure (when the
  transcript matters) it is lost; pairs with F7.
- `R/initialize_python.R:116-117`: `is_new_env` and the "Created virtual
  environment" message use `venv_dir` as given; a relative `venv_dir` makes
  the R-side check and the script's `UV_PROJECT_ENVIRONMENT` resolve against
  different bases. Fix: `normalizePath(venv_dir)` once at entry.

## 4. Questions for maintainers

- **Is runtime syncing intended?** `uv run` locks and syncs the discovered
  project by default, so `run_python_script()` can mutate `uv.lock`/`.venv`
  outside the init layer's `--frozen` discipline (F6). If unintended, is
  `--no-sync` acceptable for all host-package invocations, or do some hosts
  rely on the implicit sync?
- **`r-release.yml:188` sets `build-vignettes: false`** while the package
  declares `VignetteBuilder: knitr` and ships two vignettes, so released
  tarballs lack built vignettes. Intentional (PRISM renders docs elsewhere?)

- **Clobbering user-managed uv:** is reinstalling over an existing

## 5. What's good (preserve these)

- **The declare/materialize/runtime layering is real, not aspirational.** The
  declaration layer verifiably touches only the toml, all uv work is behind
  one subprocess boundary, and the split is documented with rationale
  (`vignettes/authoring-a-fyr-package.Rmd:31-36`). Fixes for F1/F5 should keep
  this shape: one toml module, one uv-work module.
- **The merge policy is thoughtfully specified and its happy paths are locked
  down byte-for-byte.** The case table in the roxygen
  (`R/write_group_to_pyproject.R:7-23`) matches the implementation, and tests
  like "replace_subgroup preserves sibling subgroup and trailing tables
  byte-for-byte" (`tests/testthat/test-write_group_to_pyproject.R:278`) are
  exactly the right kind of guarantee to extend (to the F1 inputs) rather than
  replace.
- **Quiet-by-default logging with per-emission threshold reads**
  (`R/zzz.R:12-22`) is a clean solution to runtime verbosity toggling in a
  library, and the scripts' strict modes (`set -euo pipefail`,
  `$ErrorActionPreference='Stop'` + explicit exit-code checks) are the right
  baseline; F7's fix should bring the R boundary up to the scripts' standard,
  not the reverse.
