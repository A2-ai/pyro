## 1. Repository map

**Purpose.** `pyro` is an R package that wraps the `uv` CLI to give R projects
reproducible, project-local Python environments. It exists to serve the "fyr"
ecosystem (sibling R packages `reportifyr` and `presentifyr`, which forward
their `initialize_*()` calls to pyro), but is usable by any R project. Codebase
type: **shared library / SDK** (R package), with two bundled **installer shell
scripts** (bash + PowerShell) that do the actual uv install / lock / sync work
as subprocesses.

**Size.** Very small: ~1,060 lines of R across 9 files in `R/`, ~230 lines of
bundled shell/PowerShell in `inst/extdata/`, ~890 lines of testthat tests.

**Entry points** (all paths absolute from repo root `/Users/jake/packages/pyro`):

- Exported R API (per `NAMESPACE`):
  - `initialize_python()`, `R/initialize_python.R:49`, the main flow: prompt,
    seed `pyproject.toml` if missing, audit pin drift, then run the platform
    setup script (install uv, `uv lock`, `uv sync`).
  - `write_group_to_pyproject()`, `R/write_group_to_pyproject.R:48`,
    idempotent merge of a dependency group into the project's
    `pyproject.toml`; called by sibling packages before they call
    `initialize_python()`.
  - `run_python_script()`, `R/run_python_script.R:35`, runs uv/Python in the
    venv via `processx::run()`; the runtime entry point host packages use.
  - `get_venv_uv_paths()`, `R/venv.R:16`; `get_uv_path()`, `R/uv_path.R:21`;
    `get_uv_version()`, `R/uv_path.R:75`; `get_proj_dir()`,
    `R/get_proj_dir.R:22`.
- Package load hook: `.onLoad` in `R/zzz.R:3` builds the log4r logger into the
  package-private env `.le`.
- Subprocess entry points invoked by `initialize_python()`:
  - `inst/extdata/uv_setup.sh` (Unix), positional args
    `<venv_dir> <toml_dir> <uv_version> [<group>...]`.
  - `inst/extdata/uv_setup.ps1` (Windows), same contract via parameters plus
    `-Groups`.

**Intended layering** (inferred from roxygen docs, `R/pyro.R`, and the two
vignettes `vignettes/how-it-works.Rmd` and
`vignettes/authoring-a-fyr-package.Rmd`):

1. Declaration layer: `write_group_to_pyproject()` mutates only the toml,
   never touches uv/network (vignette states this split is deliberate).
2. Materialization layer: `initialize_python()` seeds, audits, then delegates
   all uv work to the platform script.
3. Runtime layer: `get_venv_uv_paths()` + `run_python_script()` for host
   packages calling into the venv.
Cross-cutting under all three: the toml parsing helpers in
`R/write_group_to_pyproject.R` and the `options("venv_dir")` root cache.

**Most load-bearing files:**

1. `R/write_group_to_pyproject.R`, highest fan-in: its internal helpers
   (`read_dep_groups`, `parse_group_entries`, `render_subgroup`,
   `pkg_name_of`, `bundled_group_deps`) are consumed by
   `write_group_to_pyproject()`, `seed_pyproject()`
   (`R/initialize_python.R:175`), and `audit_pins()` (`R/audit_pins.R:36`).
   Every toml read or write in the package goes through it.
2. `R/initialize_python.R`, the only path that installs anything; every
   consumer flow starts here.
3. `inst/extdata/uv_setup.sh` / `uv_setup.ps1`, all uv install, lock, and
   sync behavior lives in these scripts, outside R test reach.

**Cross-cutting concerns:**

- Errors: `stop()` with `call. = FALSE` in most R paths; scripts use
  `set -euo pipefail` / `$ErrorActionPreference = 'Stop'` + explicit
  `$LASTEXITCODE` checks. `run_python_script` (`R/run_python_script.R:55-66`)
  catches the processx error and rethrows a bare `"<script_name> failed."`.
- Logging: log4r logger in `.le` (`R/zzz.R`), threshold filtered per-emission
  from `getOption("pyro.verbose", "WARN")`. User-facing communication is a
  separate parallel channel of `message()` calls.
- Config: three R options read at scattered sites: `venv_dir` (un-prefixed;
  read in `R/get_proj_dir.R:23`, written in `R/initialize_python.R:78-81` and
  `R/venv.R:17-21`), `uv.version` (`R/initialize_python.R:51`),
  `pyro.verbose` (`R/zzz.R:14`).
- Validation: group `name` regex-validated at `R/write_group_to_pyproject.R:51`;
  `groups` passed to `initialize_python()` are **not** validated in R (docs say
  uv validates); untrusted input is essentially the user's `pyproject.toml`,
  parsed by the hand-rolled parser.
- Concurrency: none in R (single-threaded, synchronous `processx::run`). No
  locking around concurrent toml writes from parallel R sessions.

**Build/test/CI shape:** Standard R package (roxygen2, testthat edition 3,
no compiled code). Tests mock every subprocess and filesystem boundary with
`mockery::stub` + `withr`; the shell scripts themselves have zero test
coverage, and all `initialize_python` tests carry `skip_on_os("windows")`
(`tests/testthat/test-initialize_python_groups.R`). CI:
`.github/workflows/R-CMD-check.yaml` runs a 5-cell matrix (macOS/Windows/
Ubuntu, R 4.3-4.5) using the `rv` dependency manager against an internal
PRISM registry (Windows swaps to Posit PPM); `r-release.yml` builds
tarball + multi-platform binaries; `deploy-prism.yml` publishes releases to
the internal PRISM registry.

## 2. Risk hypotheses (ranked)

### H1, The hand-rolled dep-groups parser silently corrupts valid-but-unsupported TOML on rewrite

- **Hypothesis:** `parse_group_entries` / `render_subgroup` /
  `replace_subgroup` only model "array of quoted strings", so rewriting a
  subgroup that contains other valid PEP 735 / TOML constructs (notably
  `{include-group = "other"}` inline-table items, or comments inside a
  multi-line array) drops those constructs from the user's file.
- **Signal:** `extract_quoted` (`R/write_group_to_pyproject.R:284-291`) keeps
  only quoted string tokens; `render_subgroup` (`:327-333`) re-emits only
  strings; `replace_subgroup` (`:369-423`) splices that canonical render over
  the user's original lines. The docstring at `:149-152` admits "Only handles
  the canonical `[dependency-groups]` table form with arrays of strings". The
  16 tests in `tests/testthat/test-write_group_to_pyproject.R` never include
  an `include-group` item, a comment inside an array, or a duplicate
  `[dependency-groups]` header.
- **If true, cost:** pyro's central promise ("never owns or rewrites the
  user's pins", `vignettes/how-it-works.Rmd:18-19`) is violated exactly for
  users with slightly richer tomls; corruption is silent and persisted to the
  user's project file.
- **Investigation sketch:** Construct tomls with (a) `{include-group = ...}`
  items in the target group, (b) `# comments` inside a multi-line array,
  (c) two `[dependency-groups]` headers, (d) a group defined as
  `[dependency-groups.name]` sub-table, and trace each through
  `write_group_to_pyproject()` case 4a and `audit_pins()`. Also check
  `read_dep_groups`'s block-end regex `^\s*\[` (`:166`) against multi-line
  arrays whose continuation line begins with `[`.
- **Confidence:** high (that this is worth the dig).

### H2, uv discovery/install/version policy is implemented three times and has drifted

- **Hypothesis:** the R layer (`R/uv_path.R`, `R/initialize_python.R:94-105`)
  and the two setup scripts each implement their own "where is uv, what
  version, reinstall?" policy, and they already disagree, so the uv that R
  detects/version-adopts can differ from the uv the script actually runs.
- **Signal:** `get_uv_path()` searches PATH then `~/.local/bin` then
  `~/.cargo/bin` (`R/uv_path.R:28-47`); `uv_setup.sh` searches only PATH after
  prepending `~/.local/bin` (`inst/extdata/uv_setup.sh:66-70`), never
  `~/.cargo/bin`, so a cargo-installed uv found by R triggers a fresh install
  by the script. Install sources differ: sh pulls
  `github.com/astral-sh/uv/releases/download/$version/uv-installer.sh`
  (`uv_setup.sh:54-56`) while ps1 pulls `astral.sh/uv/$Version/install.ps1`
  (`uv_setup.ps1:59`). Version adoption also happens twice: R adopts the
  installed version when `uv.version` is unset (`R/initialize_python.R:94-105`)
  and the scripts re-compare and reinstall on mismatch (`uv_setup.sh:71-80`).
- **If true, cost:** platform-divergent and machine-state-dependent behavior;
  surprise reinstalls; the version R logs is not necessarily the version that
  ran; hard-to-reproduce support tickets.
- **Investigation sketch:** Diff the three policies side by side; enumerate
  machine states (uv only in `~/.cargo/bin`; uv on PATH at a different
  version; no uv; `uv.version` set/unset) and trace which binary each layer
  picks per state on both platforms. Grep both scripts for every env var they
  read (`CARGO_HOME`, `XDG_BIN_HOME`, `UV_PROJECT_ENVIRONMENT`) and check the
  ps1 mirrors the sh's shared-filesystem workaround (`uv_setup.sh:44-49`).
- **Confidence:** high.

### H3, The session-global `options("venv_dir")` cache goes stale and misroutes every downstream path

- **Hypothesis:** `venv_dir` is written only-if-unset in
  `initialize_python()` (`R/initialize_python.R:78-81`) and unconditionally in
  `get_venv_uv_paths()` (`R/venv.R:17-21`), then trusted by `get_proj_dir()`
  (`R/get_proj_dir.R:23`) as the default for all later calls, so an explicit
  `venv_dir`/`pyproject_dir` argument or a mid-session project switch leaves
  the cache pointing at the wrong project.
- **Signal:** `initialize_python(venv_dir = X)` after the option was cached to
  Y installs at X but leaves the option at Y (the `is.null` guard at
  `R/initialize_python.R:78`); the next `get_venv_uv_paths()` then resolves
  Y's venv. The option key is un-namespaced (`"venv_dir"`, unlike
  `pyro.verbose`), so any other package setting `venv_dir` collides.
- **If true, cost:** scripts run against the wrong project's venv or audits
  read the wrong toml, silently, in multi-project R sessions (RStudio users
  switching projects without restarting R).
- **Investigation sketch:** Trace the option's write/read sites (the three
  cited above plus tests); build the state table for: fresh session, cached
  then explicit-arg call, cached then `here::here()` change. Check whether
  reportifyr/presentifyr compatibility actually requires the un-namespaced
  key (grep those repos if available; otherwise treat the key as frozen but
  the staleness as live) `[Q3]`.
- **Confidence:** medium-high.

### H4, Error context is destroyed exactly at the boundary host packages depend on

- **Hypothesis:** `run_python_script()` discards the processx error condition
  (status, stderr, system error) and rethrows a constant string, so host
  packages and end users cannot diagnose Python failures without pre-wiring a
  `stderr_callback`.
- **Signal:** `R/run_python_script.R:63-65`:
  `error = function(e) { stop(paste0(script_name, " failed."), call. = FALSE) }`,
  with `e` unused. Contrast with `initialize_python()`, which lets the raw
  processx error propagate (`R/initialize_python.R:134-143`) and prints
  captured stdout only on success (`:153`), a second, different, de facto
  error/reporting strategy at the same subprocess boundary.
- **If true, cost:** every downstream failure report reads "my_module
  failed."; debugging requires re-running with hand-rolled callbacks; the two
  subprocess boundaries behave inconsistently for the same class of failure.
- **Investigation sketch:** Compare error surfaces of the three subprocess
  call sites (`R/run_python_script.R:56-66`, `R/initialize_python.R:134`,
  `:143`, `R/uv_path.R:76`); check what a host package (per
  `vignettes/authoring-a-fyr-package.Rmd` and README usage) would actually see
  on a Python traceback with default arguments; decide whether the roxygen
  disclaimer at `R/run_python_script.R:5-9` covers losing `e` itself `[Q4]`.
- **Confidence:** high.

### H5, Test coverage is anti-correlated with risk: the install scripts and Windows path have zero coverage

- **Hypothesis:** all real risk lives in `uv_setup.sh`/`uv_setup.ps1` (network
  installs, PATH mutation, lock/sync semantics) and in Windows argument
  passing, yet tests mock `processx::run` everywhere and skip Windows
  entirely, so regressions there ship blind.
- **Signal:** every test in `tests/testthat/test-initialize_python_groups.R`
  has `skip_on_os("windows")` (lines 36, 56, 79, 103, 128, 155, 172); no test
  executes either script; the recent commit `527b624 "skip windows"` suggests
  Windows tests were disabled rather than fixed. CI runs a Windows matrix cell
  (`.github/workflows/R-CMD-check.yaml:24`) that therefore exercises almost
  nothing platform-specific.
- **If true, cost:** the PowerShell path (arg quoting via
  `processx::run("powershell.exe", ...)` at `R/initialize_python.R:123-134`,
  `-Groups` array binding, paths with spaces) can break without any signal
  until a Windows user hits it.
- **Investigation sketch:** Review `uv_setup.ps1` parameter binding against
  the `ps_args` construction (`R/initialize_python.R:124-130`), especially
  multiple groups after `-Groups` and paths containing spaces; check `bash
  -n`/shellcheck-level issues in `uv_setup.sh`; assess whether a smoke test
  (script syntax check, or a stubbed-uv script run) is feasible in CI.
- **Confidence:** medium-high.

### H6, The bundled `inst/extdata/uv.lock` is dead weight or a missed design intent

- **Hypothesis:** the 222-line bundled lockfile is referenced by no code path
  (seeding writes only a fresh toml, and the scripts run `uv lock` against the
  project), so either it is stale cruft that will drift from the bundled toml,
  or it was meant to be copied on seed to make first-init resolution
  deterministic and that never got wired up.
- **Signal:** `grep -rn "uv.lock"` over `R/` matches nothing;
  `seed_pyproject()` (`R/initialize_python.R:175-241`) writes only
  `pyproject.toml`; both setup scripts regenerate the lock from the project
  toml.
- **If true, cost:** first init resolves from the network at whatever the
  index serves that day (transitive deps unpinned), which weakens the
  reproducibility story in `vignettes/how-it-works.Rmd:47-49`; and the bundled
  lock silently rots.
- **Investigation sketch:** Confirm no consumer via grep (including sibling
  packages if reachable); check whether `uv.lock`'s contents still match the
  bundled toml's pins; decide dead-code-removal vs. copy-on-seed as the
  remediation direction `[Q6]`.
- **Confidence:** medium.

### H7, The confirmation prompt mishandles common inputs and duplicates decision logic

- **Hypothesis:** the `continue` handling in `initialize_python()`
  (`R/initialize_python.R:58-74`) treats "y"/"Y" as yes but only exact
  lowercase `"n"` as a graceful decline; `"N"`, `"no"`, and bare Enter (the
  conventional default for `[Y/n]`) all hit `stop("Must enter Y or n.")`.
- **Signal:** `tolower(continue) != "y"` then `continue == "n"` at
  `R/initialize_python.R:61-62`; the prompt text at `:284-287` advertises
  `[Y/n]`, whose convention is Enter-means-yes. Prompt strings also embed
  literal tabs/newlines from source indentation (`:280-287`, `:65-66`).
- **If true, cost:** minor UX, but this is the consent gate for installing
  software on the user's machine, so wrong handling either blocks users or
  erodes trust in the gate.
- **Investigation sketch:** Enumerate inputs `Y y n N no yes ""` through the
  branch at `:58-74`; check the single test
  (`tests/testthat/test-continue.R`) covers only the non-interactive branch.
- **Confidence:** high that it is real, low-medium that it is deep; ranked
  last accordingly.

## 3. Questions for the maintainer (defaults applied, unattended run)

1. **Q1 → H1.** The dep-groups parser documents itself as handling only
   string-array form (`R/write_group_to_pyproject.R:149-152`). Is "users must

   compatibility with existing reportifyr/presentifyr releases, and is
   mid-session project switching a supported workflow? **Default (applied):**
   the key name is compat-frozen (the vignette says `venv_dir` semantics are
   "Preserved for compatibility", `vignettes/authoring-a-fyr-package.Rmd:47-50`),
   but stale-cache behavior across explicit args / project switches is a live
   correctness concern, not intentional.
4. **Q4 → H4.** `run_python_script()` docs say stderr routing is the caller's
   concern. Does that extend to intentionally discarding the error object
   (exit status, stderr snapshot) in the rethrow at
   `R/run_python_script.R:63-65`? **Default (applied):** the routing
   disclaimer is intentional, the loss of the condition object is accidental;
   review it.
5. **Q5 → H5.** Is the Windows path (ps1 script + PowerShell arg passing)
   validated anywhere, e.g. manual QA or downstream reportifyr CI, given all
   initialize tests skip Windows? **Default (applied):** no coverage exists
   anywhere; treat the Windows/ps1 path as the largest blind spot.
6. **Q6 → H6.** Is `inst/extdata/uv.lock` meant to be consumed (copied on
   seed), or is it a leftover? **Default (applied):** treat as unreferenced;
   Pass 2 verifies no consumer and evaluates both remediation directions.
7. **Q7 → targeting.** Which matters more right now: correctness of
   toml mutation (H1) or install/bootstrap robustness (H2/H5)? **Default
   (applied):** toml mutation correctness first, it is the package's central
   written guarantee.
8. **Q8 → H7.** Is exact-`"n"`-only decline intentional (fail-closed on
   ambiguous input to an installer consent gate)? **Default (applied):**
   fail-closed on ambiguous input is intentional in spirit; the mismatch with
   the advertised `[Y/n]` convention (bare Enter erroring) is accidental.

## REVIEW ADDENDUM (survey pass, 2026-07-06)

### CONTEXT

- Codebase: pyro, an R package (~1,060 lines R + ~230 lines bundled
  bash/PowerShell) wrapping the `uv` CLI to manage project-local Python
  virtual environments (`pyproject.toml` seeding, dependency-group merging,
  uv install, lock + sync, running Python in the venv).
- Primary consumers: sibling internal R packages `reportifyr` and
  `presentifyr` (which forward their init calls to pyro), plus third-party R
  projects and R-using data scientists calling it directly. Distributed via
  an internal PRISM registry.
- Known constraints or intentional decisions worth flagging up front: the
  project's own `pyproject.toml` is the source of truth and pyro must never
  rewrite user pins (vignette `how-it-works`); `venv_dir` means the parent of
  `.venv/` and is compat-frozen naming; non-interactive sessions auto-confirm
  installation; unattended survey run, all maintainer-question defaults below
  are applied as stated.
- Areas of specific concern: hand-rolled TOML parsing/rewriting of user files;
  triplicated uv install/discovery policy (R + two platform scripts); the
  session-global `options("venv_dir")` cache; zero test coverage of the shell
  scripts and the Windows path.

### PRIORITY TARGETS

Allocate roughly 80% of effort here, as hypotheses to confirm or refute.

1. **TOML rewrite corruption (H1).** The dep-groups parser/splicer in
   `R/write_group_to_pyproject.R` (`parse_group_entries` :193-238,
   `extract_quoted` :284-291, `render_subgroup` :327-333, `replace_subgroup`
   :369-423) models only string arrays. Verify what happens on rewrite when a
   user toml contains PEP 735 `{include-group = "x"}` items, comments inside
   multi-line arrays, duplicate `[dependency-groups]` headers, or
   `[dependency-groups.name]` sub-tables; also stress `read_dep_groups`'s
   block-end detection (`^\s*\[` at :166) against array continuation lines
   starting with `[`. Trace both mutation entry (`write_group_to_pyproject`
   case 4a) and read-only consumers (`audit_pins` at `R/audit_pins.R:36`,
   `seed_pyproject` at `R/initialize_python.R:182`). The package's central
   guarantee ("never rewrites the user's pins") is the stake. [Q1]
2. **Triplicated uv policy drift (H2).** Diff the uv discovery/version/install
   policies across `R/uv_path.R:21-56`, `R/initialize_python.R:94-105`,
   `inst/extdata/uv_setup.sh:44-80`, and `inst/extdata/uv_setup.ps1:44-93`.
   Known asymmetries to start from: R searches `~/.cargo/bin`, `uv_setup.sh`
   does not; sh installs from GitHub releases, ps1 from astral.sh; version
   adoption happens in R and re-checked in scripts. Enumerate machine states
   (uv only in cargo bin, PATH uv at other version, no uv, `uv.version`
   set/unset) and determine which binary/version actually runs per state per
   platform. [Q2]
3. **Stale `options("venv_dir")` cache (H3).** Write sites
   `R/initialize_python.R:78-81` (only-if-unset) and `R/venv.R:17-21`; read
   site `R/get_proj_dir.R:23` (default for everything). Verify behavior when
   a cached session then receives explicit `venv_dir`/`pyproject_dir` args or
   switches projects: which project's venv/toml do
   `get_venv_uv_paths()`/`audit_pins()` subsequently target? The option key
   name itself is compat-frozen, do not flag the naming, but staleness and
   cross-package collision behavior are in scope. [Q3]
4. **Error-context destruction at the subprocess boundary (H4).**
   `R/run_python_script.R:55-66` discards the processx condition and rethrows
   a constant string; `R/initialize_python.R:134-153` lets raw processx errors
   propagate and prints captured stdout only on success. Assess the de facto
   error strategy across the three subprocess call sites (add
   `R/uv_path.R:75-79`) and what a host package sees on a Python traceback
   with default args. The docs' "stderr routing is the caller's concern"
   disclaimer is intentional; losing the condition object is presumed
   accidental. [Q4]
5. **Windows/ps1 blind spot (H5).** No test executes either setup script and
   every `initialize_python` test skips Windows
   (`tests/testthat/test-initialize_python_groups.R:36` etc.). Review
   `R/initialize_python.R:123-134` (`powershell.exe` invocation, `-Groups`
   array after positional args, paths with spaces) against `uv_setup.ps1`
   parameter binding, and `uv_setup.sh` for shell-level hazards; judge whether
   the CI Windows matrix cell exercises anything platform-specific. [Q5]

### OPEN HUNT

This survey spent the least time on: the GitHub Actions workflows
(`.github/workflows/r-release.yml`, 477 lines, and `deploy-prism.yml`, both
skimmed only at header level); the bundled `inst/extdata/uv.lock` (unreferenced
by code, freshness vs the bundled toml unchecked) [Q6]; `man/` roxygen output
consistency with current signatures; the vignettes' code examples versus
actual API behavior; concurrent-writer scenarios (two R sessions or parallel

### REPO MAP

**Purpose.** `pyro` is an R package that wraps the `uv` CLI to give R projects
reproducible, project-local Python environments. It exists to serve the "fyr"
ecosystem (sibling R packages `reportifyr` and `presentifyr`, which forward
their `initialize_*()` calls to pyro), but is usable by any R project. Codebase
type: **shared library / SDK** (R package), with two bundled **installer shell
scripts** (bash + PowerShell) that do the actual uv install / lock / sync work
as subprocesses.

**Size.** Very small: ~1,060 lines of R across 9 files in `R/`, ~230 lines of
bundled shell/PowerShell in `inst/extdata/`, ~890 lines of testthat tests.

**Entry points:**

- Exported R API (per `NAMESPACE`):
  - `initialize_python()`, `R/initialize_python.R:49`, the main flow: prompt,
    seed `pyproject.toml` if missing, audit pin drift, then run the platform
    setup script (install uv, `uv lock`, `uv sync`).
  - `write_group_to_pyproject()`, `R/write_group_to_pyproject.R:48`,
    idempotent merge of a dependency group into the project's
    `pyproject.toml`; called by sibling packages before they call
    `initialize_python()`.
  - `run_python_script()`, `R/run_python_script.R:35`, runs uv/Python in the
    venv via `processx::run()`; the runtime entry point host packages use.
  - `get_venv_uv_paths()`, `R/venv.R:16`; `get_uv_path()`, `R/uv_path.R:21`;
    `get_uv_version()`, `R/uv_path.R:75`; `get_proj_dir()`,
    `R/get_proj_dir.R:22`.
- Package load hook: `.onLoad` in `R/zzz.R:3` builds the log4r logger into the
  package-private env `.le`.
- Subprocess entry points invoked by `initialize_python()`:
  - `inst/extdata/uv_setup.sh` (Unix), positional args
    `<venv_dir> <toml_dir> <uv_version> [<group>...]`.
  - `inst/extdata/uv_setup.ps1` (Windows), same contract via parameters plus
    `-Groups`.

**Intended layering** (inferred from roxygen docs, `R/pyro.R`, and the two
vignettes `vignettes/how-it-works.Rmd` and
`vignettes/authoring-a-fyr-package.Rmd`):

1. Declaration layer: `write_group_to_pyproject()` mutates only the toml,
   never touches uv/network (vignette states this split is deliberate).
2. Materialization layer: `initialize_python()` seeds, audits, then delegates
   all uv work to the platform script.
3. Runtime layer: `get_venv_uv_paths()` + `run_python_script()` for host
   packages calling into the venv.
Cross-cutting under all three: the toml parsing helpers in
`R/write_group_to_pyproject.R` and the `options("venv_dir")` root cache.

**Most load-bearing files:**

1. `R/write_group_to_pyproject.R`, highest fan-in: its internal helpers
   (`read_dep_groups`, `parse_group_entries`, `render_subgroup`,
   `pkg_name_of`, `bundled_group_deps`) are consumed by
   `write_group_to_pyproject()`, `seed_pyproject()`
   (`R/initialize_python.R:175`), and `audit_pins()` (`R/audit_pins.R:36`).
   Every toml read or write in the package goes through it.
2. `R/initialize_python.R`, the only path that installs anything; every
   consumer flow starts here.
3. `inst/extdata/uv_setup.sh` / `uv_setup.ps1`, all uv install, lock, and
   sync behavior lives in these scripts, outside R test reach.

**Cross-cutting concerns:**

- Errors: `stop()` with `call. = FALSE` in most R paths; scripts use
  `set -euo pipefail` / `$ErrorActionPreference = 'Stop'` + explicit
  `$LASTEXITCODE` checks. `run_python_script` (`R/run_python_script.R:55-66`)
  catches the processx error and rethrows a bare `"<script_name> failed."`.
- Logging: log4r logger in `.le` (`R/zzz.R`), threshold filtered per-emission
  from `getOption("pyro.verbose", "WARN")`. User-facing communication is a
  separate parallel channel of `message()` calls.
- Config: three R options read at scattered sites: `venv_dir` (un-prefixed;
  read in `R/get_proj_dir.R:23`, written in `R/initialize_python.R:78-81` and
  `R/venv.R:17-21`), `uv.version` (`R/initialize_python.R:51`),
  `pyro.verbose` (`R/zzz.R:14`).
- Validation: group `name` regex-validated at `R/write_group_to_pyproject.R:51`;
  `groups` passed to `initialize_python()` are **not** validated in R (docs say
  uv validates); untrusted input is essentially the user's `pyproject.toml`,
  parsed by the hand-rolled parser.
- Concurrency: none in R (single-threaded, synchronous `processx::run`). No
  locking around concurrent toml writes from parallel R sessions.

**Build/test/CI shape:** Standard R package (roxygen2, testthat edition 3,
no compiled code). Tests mock every subprocess and filesystem boundary with
`mockery::stub` + `withr`; the shell scripts themselves have zero test
coverage, and all `initialize_python` tests carry `skip_on_os("windows")`
(`tests/testthat/test-initialize_python_groups.R`). CI:
`.github/workflows/R-CMD-check.yaml` runs a 5-cell matrix (macOS/Windows/
Ubuntu, R 4.3-4.5) using the `rv` dependency manager against an internal
PRISM registry (Windows swaps to Posit PPM); `r-release.yml` builds
tarball + multi-platform binaries (477 lines, skimmed only) (?);
`deploy-prism.yml` publishes releases to the internal PRISM registry
(skimmed only) (?).
